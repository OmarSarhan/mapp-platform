# Semantic metadata control plane

Semantic service `1.1.0` is a metadata control plane beside the data plane. It gives
the dashboard, standalone CLI, and approved agents a durable description of a
data asset without making the semantic service a database proxy. In v1, the
private semantic service stores generated source facts and reviewed human
meaning; it has no database credential and never executes source queries or
exposes source rows. The public configuration service can separately read the
strictly bounded sample or statistics described under **On-demand Gemini
drafts**, but only for an explicitly authorized generation request. Those
values go to Gemini and are not added to the semantic catalog or returned to
the caller.

## Architecture and trust boundary

```text
dashboard / standalone CLI
             │ authenticated public API and semantic scopes
             ▼
        configuration service
          │              │
          │              ├── runtime reader ──> allowlisted PostgreSQL
          │              │       (catalog/comments; optional bounded Gemini
          │              │        sample/statistics only with semantic:data)
          │              │
          │              └── derived owner ──> PostgreSQL/PostGIS
          │                    │ same transaction
          │                    └── derived definition + semantic outbox
          │
          └── internal token ──> semantic service ──> var/semantic/semantic.sqlite3
```

Only the configuration service is public through Caddy. It authenticates the
dashboard session or CLI bearer token, enforces semantic scopes, and forwards
the trusted actor and effective scopes. The semantic service is attached only
to the internal `semantic-control` Compose network. It has:

- no published host port;
- no PostgreSQL credential or database network;
- a read-only container root and a single writable `var/semantic` mount; and
- one internal bearer token shared only with the configuration service.

The internal token authenticates service-to-service traffic. It is not a user
credential and must never be returned to a browser, CLI, log, proposal, or
artifact. `SEMANTIC_INTERNAL_TOKEN` is generated by `./bin/mapp init`; an
existing installation can add a missing key with
`./bin/mapp doctor --add-missing`.

## Profile model

Each catalog asset has two deliberately separate sections:

- `generated` contains source-owned facts such as the binding, relation kind,
  definition digest, source relations, columns and types, geometry, SRID,
  identifier column, and lifecycle timestamps. Only trusted lifecycle events
  can change it.
- `curated` contains reviewed meaning such as a display name, description,
  tags, caveats, and annotations. It changes only through a semantic proposal.

Generated facts are read-only in the dashboard and CLI. A curator does not
silently override a source fact, and a source refresh does not silently erase
curated meaning.

An asset receives a logical UUID when its derived relation is created. That ID
stays the same through replacement and refresh. A generated field receives its
own logical ID; the ID is retained while the field name remains present across
source generations. Removing a field moves any keyed curated annotation to the
asset's `orphans` collection with the removed field ID, name, annotation, and
generation. A later field with that name is not assumed to be the same field.
`curated.fields`, when present, must be an object keyed only by active stable
field IDs. Each annotation must be an object with at most 64 top-level
properties and 16 KiB of encoded content; the complete field annotation map is
limited to 1 MiB. Proposal check and apply both enforce this against the
transactionally current generated profile.

Dropping a managed relation emits an archive event. The semantic asset and its
history remain as an immutable tombstone instead of being deleted. Archived
assets cannot receive new source events or curated proposals. This preserves
the meaning and audit trail of references seen in older proposals or external
records. Catalog export, search, and derived-profile collections omit archived
assets for every caller, including administrators. An ordinary inspector also
receives `404` from an exact archived asset or history lookup. A dashboard
administrator, legacy `full` token, or bearer token with both
`semantic:inspect` and `semantic:admin` can still retrieve the exact asset and
history by a previously recorded asset ID for audit; archival is therefore
concealment from normal discovery, not deletion of history.

Every accepted source event and applied curated proposal records a complete
asset-history snapshot. The catalog also has a monotonically increasing global
revision, while each asset has its own optimistic-locking `version` and source
`generation`.

Authenticated clients can read that chronological history through
`GET /api/semantic/catalog/objects/<asset-id>/history`. The gateway applies the
same asset visibility check as the ordinary object read, and the returned
history and top-level `catalogRevision` come from one semantic-store snapshot.
The dashboard loads this immutable history on request and displays retained
orphaned field annotations separately from the active profile.

## Allowlisted PostgreSQL sources

Ordinary PostgreSQL tables and views can be registered without first creating
a managed derived relation. Source discovery and synchronization require both
`semantic:inspect` and the separate `semantic:source` scope. The latter is a
database-metadata authority: it is included in the AI semantic author and
semantic administrator presets, but not reader, proposal author, curator, or
delivery operator presets.

`SEMANTIC_SOURCE_ALLOWLIST` is a comma-separated list of
`ALIAS:schema.relation` or `ALIAS:schema.*` entries and defaults to
`MAPP:leeds.*`. Alias matching is exact and case-sensitive. An explicitly
empty value disables source discovery. PostgreSQL system schemas and
`derived_layers` are rejected even if an operator attempts to allowlist them.
Underscore-prefixed relations are internal control tables and are likewise
never discoverable or synchronizable as semantic sources; this excludes ETL
run records such as `leeds._etl_runs` and `leeds._census_etl_runs`.
`SEMANTIC_SOURCE_EXCLUSIONS` uses the same selector syntax to exclude named
internal relations without changing code; the bundled example excludes
`MAPP:leeds.census_datasets`.

An exclusion takes effect immediately for future discovery and synchronization;
it does not retroactively change an asset already stored in the semantic
catalog. An operator with `semantic:inspect` and `semantic:admin` can explicitly
archive every ready PostgreSQL source asset that now matches this setting
through `POST /api/semantic/source/archive-excluded` with
`{"confirmed": true}`. Record the returned asset IDs before leaving the audit
workflow: archived assets disappear from catalog export, search, and
derived-profile collections even for administrators, while exact administrator
asset/history reads remain available by ID. Archival never changes the
underlying PostgreSQL relation, and removing an exclusion later does not
unarchive its tombstone.

The dashboard also exposes **Archive semantic profile** for one selected ready
asset. It calls
`POST /api/semantic/catalog/objects/<asset-id>/archive` with
`{"confirmed": true}` and requires the same `semantic:inspect` plus
`semantic:admin` authority. This removes the semantic profile from normal
discovery while retaining its audit history and leaving the database relation
and its rows untouched. It is different from unsetting a curated annotation,
which keeps the active generated profile discoverable.

Discovery uses the exactly configured `DBS_<ALIAS>` read-only credential and
returns only relations for which that role currently has schema `USAGE` and
relation `SELECT`. Synchronization starts a repeatable-read, read-only
transaction, takes an `ACCESS SHARE` relation lock, and reads only PostgreSQL
catalog metadata: relation kind, ordered column names and formatted types,
nullability, valid non-partial single-column identity indexes, geometry
typmods, and bounded standard table/column comments. It never selects from the
relation, samples values, or reads defaults or expressions. Missing,
disallowed, concurrently changed, or no-longer-selectable relations fail
closed.

Source asset identity is a deterministic UUID over the database alias, schema,
and relation. A first synchronization registers generation 1; a changed
metadata digest emits the next refresh generation, retaining field IDs for
unchanged column names and orphaning annotations for removed fields. An
unchanged digest is a no-op: no event, asset version, generation, or catalog
revision is created. The dashboard and CLI expose discovery and explicit
register/sync actions; the resulting catalog asset can then be selected for
table- or field-level Gemini generation.

## Managed derived-layer lifecycle

Creating, replacing, refreshing, or dropping a managed derived relation writes
its semantic intent to `derived_layers._semantic_outbox` in the same
PostgreSQL transaction as the database change. Therefore a successful derived
commit cannot omit the corresponding semantic event merely because the
semantic service is temporarily unavailable.

The `derive` permission is sufficient to create the automatically generated
semantic profile. The user does not also need `semantic:propose` or
`semantic:apply`: those scopes protect later edits to curated meaning, not
source-owned registration.

After the database transaction commits, the configuration service wakes the
outbox worker. It also drains outstanding work in the background and at
startup. Delivery uses a stable event ID, payload hash, and increasing
generation, so retrying the same event is idempotent and an older generation
cannot overwrite a newer source profile. Before sending, the configuration
service verifies the retained event envelope and payload hash. It accepts an
acknowledgement only when the event ID, payload hash, asset, generation,
resulting status, and catalog revision match the dispatched event.

Eligible head events are atomically claimed in PostgreSQL with a unique claim
ID and bounded expiry. `FOR UPDATE ... SKIP LOCKED` plus the unexpired lease
prevents multiple workers from owning the same event, and delivery, retry, or
repair state can be committed only by the matching claimant. An expired lease
makes the event eligible after a worker crash. Delivery is at-least-once, not
exactly-once: a dispatch repeated across lease expiry is safe because the
semantic service deduplicates the stable event ID and requires the same payload
hash.

Delivery is strictly ordered per asset and managed derived name: a later
generation or replacement asset remains blocked until every earlier event for
that identity is delivered. Connectivity and server failures use bounded
exponential backoff, capped at five minutes. A permanent 4xx response
transitions the event to `repair_required` immediately; eight failed delivery
attempts do the same.

A live managed definition reports one of these public profile states:

| State | Meaning |
| --- | --- |
| `registering` | The database change and durable outbox event committed, but the matching semantic generation is not yet confirmed. |
| `ready` | The semantic service accepted the current generation and returned its catalog revision. |
| `repair_required` | Delivery returned a permanent conflict or exhausted its bounded retries; the retained event blocks later generations until an administrator resolves the cause and explicitly retries it. |

Transient retry details stay in the private outbox rather than becoming
another public profile state. The route named `repair` is a confirmed
administrator retry restricted to `semantic:admin`. It requeues the same event
and payload; it does not edit semantic facts or correct a deterministic
conflict. A deterministic 4xx, corrupt event, or invalid acknowledgement will
fail again until its underlying cause is fixed.

Ordinary `semantic:inspect` derived-profile reads expose the public readiness
state, not private outbox rows. An administrator session, legacy `full` token,
or a token with both `semantic:inspect` and `semantic:admin` also receives an
optional name-level `delivery` diagnostic for the blocking event: its event ID,
operation, generation, state, attempt count, and a bounded single-line error.
The response does not expose the retained payload, claim ID, or database
connection.

If a dropped relation's archive delivery fails after its local definition has
been deleted, administrative list responses include it separately in
`deliveryBlockers`. The dashboard and CLI show the dropped relation, retained
event identity, operation, generation, attempts, and bounded error, and permit
the same confirmed repair by name. Retrying an archive reports
`pending_archive`, not `registering`. Ordinary inspectors receive neither
matched delivery diagnostics nor unmatched blockers.

The top-level `catalogRevision` on a derived-profile response is fetched from
the live semantic service. The per-profile `revision` remains the last accepted
delivery acknowledgement, but it is not used to invent a catalog revision. If
the service is unavailable, the route returns `503` without a
`catalogRevision`; an invalid upstream revision fails as a bad gateway
response.

New workspace publication that introduces a reference to
`derived_layers.<name>` is allowed only when that relation's current semantic
profile is `ready`. An existing reference may remain unchanged or be removed
while registration is unavailable: retaining it produces a warning, while
removal remains allowed. This fail-closed check prevents new dependencies on
incompletely registered data without turning a semantic-service outage into an
inability to clean up the workspace.

Derived database mutation and workspace publication remain separate approvals.
Creating a relation and its generated semantic profile does not add it to the
workspace. Replacing a relation does not approve the dashboard's unsaved
follow-on field reconciliation.

## Curated proposal workflow

Semantic changes use the same inspect, propose, review, approve, and apply
shape as workspace changes, but are revision-bound to one semantic asset:

1. Inspect or search the catalog and read the asset's current `version`.
2. Check a non-empty set of `set` or `unset` operations below `/curated`,
   optionally with a concise explanation.
3. Review the server-produced focused diff and fingerprint from the check.
4. Create the exact checked proposal. Creation does not apply it.
5. Before applying, fetch and review the exact stored pending proposal,
   including its explanation and focused diff.
6. Apply only after explicit approval, or explicitly confirm decline with an
   optional reason.

The dashboard enforces step 5: **Apply** remains disabled until it has fetched
`GET /api/semantic/proposals/<id>` and rendered that stored proposal's
explanation and focused diff. A proposal-list summary is not review evidence,
and switching proposals invalidates the previous review.

Catalog export, search, asset show/history, derived-profile, and proposal
reads are JSON-first CLI inputs suitable for an approved agent. They inform a
proposal; they do not grant data access or turn the original request into
approval to apply.

To remove reviewed meaning without deleting database data or generated source
facts, check an `unset` operation for only the relevant curated path. For
example, unset `/curated/description` for one table-level value,
`/curated/fields/<field-id>/description` for one field property, or
`/curated/fields/<field-id>` for that field's complete curated annotation.
Then use the same fingerprint/create/review/approval/apply workflow. Generated
columns cannot be deleted through a curated proposal: they continue to reflect
the source relation until a trusted source refresh removes them. Archiving the
whole profile is the separate administrator lifecycle action described above.

## On-demand Gemini drafts

The dashboard and standalone CLI can request a table-level or field-level
semantic draft from Gemini. `POST /api/semantic/generate` accepts only an
`assetId` and either `{ "kind": "table" }` or
`{ "kind": "field", "fieldId": "<stable-id>" }`. The field form uses the
generated field ID rather than its mutable display name. An optional closed
`contextOptions` object accepts the independent boolean properties
`sampleRows` and `statistics`; both default to `false`.

Generation requires both `semantic:inspect` and `semantic:generate`. This is an
intentional egress-and-cost boundary: inspect permission alone cannot send
metadata to an external model, while generate permission alone cannot reveal
an asset. Admin-only assets still require `semantic:admin` in addition to
those two scopes and remain indistinguishable from missing assets otherwise.
Requesting either data-derived context option additionally requires
`semantic:data`. Existing generation tokens therefore remain metadata-only.

The configuration service always sends a bounded metadata prompt. A table prompt
contains whitelisted table identity, binding, type/geometry facts, generated
field names and types, bounded PostgreSQL table and column comments, and the
four current table annotation keys. A field prompt contains the same table
identity, only the selected field and its bounded source comment, and only that
field's current annotation. By default it excludes rows, sample values, defaults,
expressions, raw SQL, source lists, actors, definition digests, orphan
annotations, and annotations for other fields. Metadata values are treated as
untrusted prompt data.

The dashboard's **What Gemini receives** disclosure offers two unchecked
options in both Guided and Advanced modes:

- **5% sample of row data** sends at most 100 rows or 96 KiB, whichever is
  reached first. A table draft includes at most 20 eligible profile fields; a
  field draft includes only its selected field. Geometry and binary values are
  omitted, each serialized value is limited to 512 characters, and a sample
  may be empty.
- **Table/column statistics** sends a planner row estimate and column counts
  for a table draft, or bounded aggregate counts and text-length statistics
  calculated over at most 1,000 rows from a 5% sample for a field draft. It
  does not send the values used to calculate those aggregates.

Both reads use profile-owned identifiers, a read-only transaction, short
statement and lock timeouts, and an `ACCESS SHARE` lock. Before reading values,
the locked live column names and types must exactly match the stored generated
profile. Synced source assets are rechecked against the configured allowlist
and exclusions. Managed derived assets must also have the same current, ready
semantic generation and are queried under the derived reader role. Sample rows
are sent only to Gemini: they are never returned to the browser or CLI and
never written to the audit log.

Gemini returns a closed structured object containing `displayName`,
`description`, `tags`, and `caveats`. The server validates and bounds that
object, discards exact no-ops, and constructs the JSON Pointer paths itself.
The response is only a version-bound `draft` with targeted `/curated`
operations. It does not check, retain, create, approve, or apply a proposal.
The user or agent must still run the ordinary semantic check and proposal
workflow and review the focused diff. Generated wording can be wrong even when
it satisfies the schema. A bounded sample or estimate is non-exhaustive and is
not evidence of completeness, quality, uniqueness, or sensitivity.

`GET /api/semantic/status` advertises whether generation is available, the
configured model, supported targets, and each optional context cap. The
optional `GEMINI_APIKEY` and `GEMINI_MODEL` settings are passed only to
`config-ui`; they are not present in the browser, CLI, semantic service, XYZ,
browser runner, or Caddy. Provider requests are one-shot, set `store: false`,
reject redirects, have bounded request/response sizes and timeouts, and are
never retried automatically. A batch of up to ten selected fields is submitted
concurrently, progress is reported as requests complete, and the ordered draft
is shown only after the whole batch succeeds. `store: false` does not override the Gemini
project's data-use and retention terms; operators must select an appropriate
billing or [zero-data-retention configuration][gemini-zdr] under the
[Gemini API terms][gemini-terms], and grant generation only for metadata they
are authorized to disclose. Audit entries contain the actor, asset/field
identity, target, provider, model, selected option booleans, bounded row count,
statistics scope, and outcome code, never the key, prompt, sampled values, or
generated values.

The status response's `schemaVersion` identifies the semantic store/API data
shape supported by that deployment. `catalogRevision` is a monotonically
increasing snapshot revision for the whole semantic catalog. It is neither an
asset count nor interchangeable with an asset's `version`, source
`generation`, or the workspace revision. Clients should report both values for
diagnostics, use the per-asset `version` for semantic proposals, and always
consume the revision returned with the particular catalog/search/history
snapshot they inspected.

Catalog, search, asset-history, derived-profile, source-relation, and proposal
collections use the platform's pagination contract `1`: at most 100 items per
response, an opaque continuation cursor, and a null `nextCursor` at the end.
The CLI keeps one page in memory and requires an explicit cursor for the next
page. If the catalog revision, source configuration, or visible boundary
changes, restart from the first page when the service rejects an expired
cursor. Storage queries resume from the cursor key and fetch only `limit + 1`
rows. Source-relation discovery orders by alias, schema, and relation, applies
allowlist and exclusion rules before the database limit, and binds its cursor
to the platform instance plus a keyed digest of effective source configuration,
without exposing connection credentials as a public verifier. Each alias
query uses a read-only repeatable-read transaction, but pages do not share a
catalog snapshot: concurrent relation creation or deletion follows ordinary
keyset semantics. A semantic response may be shorter than `limit` when its 16
MiB page budget is reached, so only a null `nextCursor` means completion; one
item that cannot fit fails with `page_too_large` rather than being truncated.
Parameterless compatibility reads keep their old response shape only through
100 items and return `pagination.required` above that threshold or when the
legacy response would exceed its byte budget. They fetch at most 101 records to
make that decision. Parameterless search still returns its historical first 20
matches when no more than 100 exist, while using the 101-row probe to detect
overflow.

For administrator derived-profile reads, delivery diagnostics are bounded
separately. The service selects at most one blocker for each displayed profile.
On the first page it also returns a repair-work batch of at most 100 unmatched
archive blockers. `deliveryBlockersMore: true` means the administrator should
repair the displayed batch and refresh the first page; later profile pages do
not repeat unmatched blockers. First-party consumers accept only a literal JSON
boolean for this flag, and the CLI rejects a flag without its accompanying
blocker array. The complete profiles, blockers, pagination, and diagnostic
envelope must remain under the advertised response ceiling.

Roll out the contract-1.4-aware CLI first. Then deploy semantic service 1.1.0
together with the matching `config-ui` image, which packages the gateway and
its bundled dashboard as one platform artifact. That dashboard sends
`limit=100`, keeps independent cursors for catalog, source, derived profile,
proposal, and asset-history views, and loads another page only on an explicit
user action. An older browser session remains compatible through 100 items and
receives an actionable pagination error above that threshold; refresh it onto
the dashboard bundled with the new gateway.

[gemini-terms]: https://ai.google.dev/gemini-api/terms
[gemini-zdr]: https://ai.google.dev/gemini-api/docs/zdr

Applying is atomic only while the asset still has the proposal's
`baseVersion`. A generated lifecycle event or another applied proposal
increments the version, so stale proposals return a conflict and must be
re-inspected and recreated; they are never silently rebased. Proposal states
are `pending`, `applied`, and `declined`. The checked explanation is included
in the fingerprint and retained with the proposal. The proposal's `actor`
always identifies its creator. Apply and decline record the separate decision
identity and timestamp in `decidedBy` and `decidedAt`; both are null while a
proposal is pending, and may remain null on migrated legacy decisions whose
original decision actor or time is unknown.

Semantic authorization is independent from workspace authorization:

| Scope | Capability |
| --- | --- |
| `semantic:inspect` | Status, catalog export/search/show/history, derived-profile reads, and proposal reads |
| `semantic:source` | Discover and synchronize allowlisted PostgreSQL catalog metadata; also requires `semantic:inspect` |
| `semantic:generate` | Request an external draft using semantic metadata; also requires `semantic:inspect` |
| `semantic:data` | Explicitly permit bounded sample rows or data-derived statistics in a Gemini request; also requires the generation and inspect scopes |
| `semantic:propose` | Check and create curated proposals; decline pending proposals |
| `semantic:apply` | Apply an explicitly approved pending proposal |
| `semantic:admin` | Confirmed retry of a retained derived-profile event; combine with `semantic:inspect` for source/profile archival and exact-ID admin visibility |

New device credentials include `semantic:inspect` by default.
`semantic:source`, `semantic:generate`, `semantic:data`, curated proposal, and apply rights must
be granted deliberately. Narrow scopes are not hierarchical: for example, a
bearer token that synchronizes a source needs both `semantic:inspect` and
`semantic:source`, while one that inspects and retries a profile event needs
both `semantic:inspect` and `semantic:admin`. The API route retains the name
`repair`, but it does not promise that retry can resolve a deterministic
conflict. An administrator dashboard session has the corresponding
administrative access.

The dashboard's **Access and audit** panel offers semantic reader, proposal
author, AI semantic author, curator, delivery operator, semantic
administrator, and full platform operator presets. Expanding
**Customize narrow scopes** permits an exact workspace-and-semantic scope
selection. Presets are only provisioning conveniences; the stored scopes and
server-side checks remain authoritative.

See [Configuration API contract](api-contract.md) for routes and
machine-readable discovery. The separate CLI repository owns the client
commands; no CLI implementation belongs in this repository.

## Deployment and operations

Persistent semantic state lives under ignored runtime state:

```text
var/semantic/
└── semantic.sqlite3       generated, curated, proposal, event, and history state
```

SQLite uses a write-ahead log while the service is running, so treat the whole
directory as one state unit. Preserve owner-only directory and database modes.
Do not commit it, add it to a container build context, or mount it into XYZ.
Durable does not mean backup-free: v1 has no automatic history pruning,
off-host replication, or retention scheduler.

Useful operational checks are:

- `./bin/mapp ps` for `semantic-service` and `config-ui` health;
- the authenticated semantic status route for schema and catalog revision;
- the source relation list for allowlist and read-role visibility;
- the derived-profile list for `registering` or `repair_required` entries; and
- service logs plus the private outbox state when registration does not
  converge.

For Gemini drafts, also check the `capabilities.generation` status object.
`available: false` means the optional key is missing or its local configuration
is invalid. Rate limits and timeouts are reported distinctly and do not trigger
an automatic retry.

Do not edit the SQLite database or `_semantic_outbox` manually. First allow
automatic retry. For `repair_required`, identify and correct the underlying
cause, then use the confirmed administrator retry. The retained event remains
unchanged, so retrying without correcting a deterministic failure will
reproduce it. Recovery is not permission to invent curated annotations.

The destructive bundled-database `reset-data --confirm` operation preserves
this history. Beginning reset installs a durable PostgreSQL maintenance gate
with a unique operation owner under the same advisory lock used by derived
mutations. New creates, replacements, refreshes, drops, and confirmed
administrator delivery retries are rejected while the gate is active,
including background operations accepted just before reset. Automatic outbox
delivery remains active because reset needs it to complete both preflight and
archival. Synchronous API maintenance conflicts return `409` with
`derived_layer.maintenance`.

While holding the gate, reset first waits until every current profile is
`ready` and no undelivered outbox event remains. A `repair_required` blocker or
bounded preflight timeout aborts without queuing archive events. Only after
that preflight succeeds does reset archive every current asset. It removes the
PostgreSQL volume only when every current profile is an archived tombstone and
the outbox is again completely delivered.

The owner identity fences compensation as well as reset: a concurrent reset is
rejected, and its failure handler cannot recover another operation's gate. On
a handled failure or signal after the archival phase begins but before volume
removal, the owning wrapper restarts the private control plane and compensates
each definition left in reset archival state. It assigns a new semantic asset
ID and generation 1, emits a registration event naming the archived asset as
its audited predecessor, and waits for the replacement profile and all retained
events for that derived name to become delivered and `ready`. The semantic
service accepts that predecessor only when it is archived and its name and
binding match. It then carries forward the predecessor's curated profile,
orphans, and visibility, retaining field IDs for matching field names. The
recovery actor and predecessor link are retained in the successor's history.
The old asset remains an immutable tombstone; recovery never unarchives it or
reuses its ID. The owner-qualified maintenance gate remains active until an
in-transaction completion check confirms those successor profiles are ready;
ordinary derived mutations cannot enter during that wait.

Service startup deliberately does not force recovery of a retained reset gate,
because it cannot prove that the owning reset process has stopped. If a
process or host interruption prevents owned compensation, keep the database
volume, confirm that no `reset-data` process remains, and run:

```sh
./bin/mapp recover-reset-data --confirm
```

That explicit command force-recovers the retained gate. It is not a substitute
for stopping a live reset. If a reset archive or successor registration reaches
`repair_required`, first correct its cause and rerun this confirmed recovery
command. Its owner-pinned recovery path requeues only the exact retained reset
event and payload; the ordinary administrator retry remains blocked by the
maintenance gate, and no retry can repair a deterministic conflict by itself.
If the database volume has already been removed, semantic compensation is no
longer safe or applicable; run the confirmed reset again to finish
initialization.

Back up the semantic directory together with PostgreSQL, the workspace, and
control state. Stop configuration writes and the semantic service before
copying the SQLite directory so the database and any WAL files form one
consistent unit. Coordinate the PostgreSQL dump or external snapshot from the
same write-quiesced interval because the derived outbox is the recovery bridge
between the two stores. The detailed sequence is in
[Backup and restore](backup-restore.md).

## V1 boundary and future optionality

V1 deliberately provides metadata and governance, not a universal analytics
engine. It does not:

- execute user queries, metrics, functions, or semantic expressions;
- hold database credentials or return source rows;
- infer business meaning with embeddings or an AI model;
- provide a generic connector framework for arbitrary data systems;
- implement row- or column-level data authorization; or
- expose computed functions while hiding their underlying data.

Those are possible later layers, but should not be folded into this service.
When a real second data location is introduced, prefer a source-specific
collector that owns only that source's narrow read credential and emits the
same closed generated-event contract. The semantic store can then retain a
logical binding without learning how to query every physical system.

If governed metrics or functions are added, keep their definitions in the
semantic control plane and run them through a separate executor container with
its own narrow credentials, query allowlist, resource limits, and result-level
authorization. That separation keeps metadata inspection safe when data moves
to another store and avoids granting an AI agent database access merely so it
can understand the catalog.
